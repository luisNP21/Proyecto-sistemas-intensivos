# Static correctness review: AWS data pipeline (Terraform + Python)

Static verification of the Terraform (`~> 5.60` AWS provider) and Python for the traffic pipeline, since `terraform validate` could not run. Scope is correctness only: things that would break `init` / `validate` / `apply`, or make the pipeline not work. Every resource/attribute name you asked about is valid under provider 5.60; the real correctness risks are architectural: the batch Lambda's reachability inside the VPC and one Spark streaming sink.

**Watch for:** Batch Lambda in-VPC reachability is implicit — the interface endpoints that give Secrets/Logs/CloudWatch a private path are created only because `enable_vpc_endpoints` defaults to `true` in the `network` module, but `main.tf` never sets or depends on it, and the S3 gateway endpoint's `route_table_ids` come from `data.aws_route_tables.default`; if that misses the Lambda's subnets, S3 writes hang until the 300s timeout — **likely**. Spark's invalid-rows stream `q_bad` is never awaited independently (`q_agg.awaitTermination()` blocks first), so a failure in `q_bad` alone won't stop the driver — **confirmed**. JDBC append into a PK table under `update` mode throws on re-emitted windows — **confirmed**. The `check` block, `data.aws_region.current.name`, QuickSight block names, and IoT `sqs {}` attributes are all valid.

**Verdict**: NEEDS_CHANGES

## High-level view

The provider-name questions you raised are mostly non-issues. `aws_emrserverless_application` (`network_configuration`, `auto_start_configuration`, `auto_stop_configuration`, `release_label`, `type="spark"`), the QuickSight block/attribute names (`parameters.postgresql`, `credentials.credential_pair`, `vpc_connection_properties`, `physical_table_map`, `relational_table.input_columns`, `permission` singular on the data source vs `permissions` plural on dataset/dashboard, `data_set_identifiers_declarations`), the IoT `sqs {}` block (`queue_url`, `role_arn`, `use_base64`), the `aws_vpc_security_group_*_rule` attribute names, `data.aws_region.current.name`, and the top-level `check` block with `var.*` references are all valid for `~> 5.60`.

The correctness risks are architectural, not syntactic. The batch Lambda runs in the default VPC's subnets with an egress-only SG and reaches AWS APIs through VPC endpoints. The interface endpoints (`secretsmanager`, `logs`, `monitoring`) cover every service the handler calls and exist because `enable_vpc_endpoints` defaults to `true` in the `network` module — but `main.tf` never sets or depends on it, so that reachability is implicit. The residual hole is S3: its gateway endpoint binds to `data.aws_route_tables.default.ids`, and if that doesn't cover the Lambda's subnets the first Parquet write hangs until the 300s timeout.

The DDL bootstrap and the EMR job launch both run Python via `local-exec` with `interpreter = ["python","-c"]` and heredocs. These interpolate Terraform `${...}` directly into Python source. The RDS DDL path is Windows-safe (it uses `replace(..., "\\", "/")`), but the here-strings embed values like bucket names and a secret name unescaped into Python string literals; benign for these inputs but fragile.

The Python handlers are largely sound. The batch handler's watermark/upsert logic is coherent and matches the schema. The Spark job's second stream (`q_bad`) writes invalid rows as JSON append with its own checkpoint, and `q_agg.awaitTermination()` blocks before `q_bad.awaitTermination()` is reached — both queries are already started so this runs, but it means a failure in `q_bad` alone won't stop the driver.

### EMR Serverless capacity: validates, but cold-starts

`aws_emrserverless_application` accepts `network_configuration`, `auto_start_configuration`, `auto_stop_configuration`, `release_label`, and `type = "spark"` as written. `maximum_capacity { cpu, memory }` (optionally `disk`) is also a valid application-level block, so this validates and applies. The gap is the absence of `initial_capacity`: without pre-warmed workers the app cold-starts on every `start_job_run`, which for a long-running streaming job means a multi-minute delay before the stream begins processing. Add warm capacity if that latency matters:

```hcl
initial_capacity {
  initial_capacity_type = "Driver"
  initial_capacity_config {
    worker_count = 1
    worker_configuration { cpu = "2 vCPU", memory = "4 GB" }
  }
}
initial_capacity {
  initial_capacity_type = "Executor"
  initial_capacity_config {
    worker_count = 2
    worker_configuration { cpu = "2 vCPU", memory = "4 GB" }
  }
}
```

### Batch Lambda reachability inside the VPC

`main.tf` runs `lambda_batch` with `subnet_ids = module.network.subnet_ids` and `security_group_ids = [module.network.compute_security_group_id]`. That SG is egress-only to `0.0.0.0/0`. Reachability to AWS APIs then depends on one of two paths: a public route on the subnets, or the VPC endpoints. The `network` module builds S3 gateway + interface endpoints (`secretsmanager`, `logs`, `monitoring`) under `enable_vpc_endpoints`, which defaults to `true` in the module — but `main.tf` never sets it from the root, so the behavior is implicit. The interface endpoints cover every service the batch handler calls (`get_secret_value`, S3 `put/get`, CloudWatch `PutMetricData`), which is the saving grace.

The residual risk is the S3 path. The interface endpoints give Secrets/Logs/CloudWatch a private DNS path, but S3 goes through the gateway endpoint, which attaches to `data.aws_route_tables.default.ids`. If that data source returns no route tables (or not the ones backing the Lambda's subnets), the in-VPC Lambda has no path to S3 and will hang until its 300s timeout. The handler's first S3 write is `_put_parquet`; the symptom is a timeout after reading the DB. Make `enable_vpc_endpoints` explicit from the root and confirm the route-table association covers the Lambda's subnets.

The endpoint resources inside `network` are internally consistent (SG, ingress rule, gateway and interface endpoints all gated on the same `enable_vpc_endpoints`, no dangling `[0]`), so the only gap is that the root neither sets the flag nor depends on the endpoints — whether they exist is invisible from `main.tf`. Set it explicitly.

### `local-exec` heredoc interpolation

The RDS DDL path handles Windows paths correctly via `open(r"${replace(var.ddl_sql_path, "\\", "/")}", ...)` and passes the password through `environment { PGPASSWORD = ... }` rather than interpolating it. The EMR module does not follow that pattern: it injects `${var.artifacts_bucket}`, `${var.secret_name}`, `${var.region}`, and `${aws_emrserverless_application.this[0].id}` straight into Python string literals. Current values contain no quotes or backslashes so it works today, but any value that does will break the generated Python, and the secret name lands in the rendered plan. Harden it by passing these through `environment {}` and reading `os.environ`, matching the RDS module.

### Spark streaming sinks

Two concerns in the stream. First, `foreachBatch` writes to PostgreSQL in JDBC append mode against a table with PK `(ventana_inicio, ciudad, avenida)`. In `update` output mode a window can be re-emitted as late data arrives within the 2-minute watermark; the re-emission is an append, so it hits a duplicate-key violation and fails the batch. The in-code comment acknowledges the trade-off ("PK evita duplicados si el batch es estable"), but under late data it throws rather than upserts. Use a staging table + `ON CONFLICT ... DO UPDATE` if late data is expected.

Second, the invalid-rows stream:

```python
q_agg.awaitTermination()
q_bad.awaitTermination()
```

Both queries are started before these lines, so both run. But `q_agg.awaitTermination()` blocks indefinitely for a streaming query, so `q_bad.awaitTermination()` is only reached if `q_agg` stops. If `q_bad` fails on its own, the driver keeps running on `q_agg` and the failure is silent. Use `spark.streams.awaitAnyTermination()` if you want either failure to surface.

### Cross-module wiring

The root-to-module wiring checks out. Every output referenced exists: `module.network.rds_security_group_id`, `compute_security_group_id`, `subnet_ids`; `module.secrets.db_password/secret_arn/secret_name`; `module.rds.endpoint/port/jdbc_url`; `module.storage.data_bucket(_arn)/artifacts_bucket(_arn)`; `module.messaging.queue_url/queue_arn/dlq_name`; `module.lambda_batch.metric_namespace/function_name`; `module.emr_serverless.application_id`; `module.quicksight.dashboard_url`. Types line up: `security_group_ids` is always passed as a one-element list `[module.network.*]` into modules declaring `list(string)`, and `subnet_ids` flows through as the `data.aws_subnets.default.ids` set into `list(string)` inputs (Terraform coerces the set to a list here).

`module.rds.port` is a number and feeds both `aws_secretsmanager_secret_version.db` (inside `jsonencode`, fine) and `module.quicksight.rds_port` (declared `number`, fine). The batch Lambda env var contract matches: the module sets `METRIC_NS` and the handler reads `os.environ.get("METRIC_NS", ...)`.

### Provider attribute names you asked about — all valid

`aws_iot_topic_rule`'s `sqs {}` block uses `queue_url`, `role_arn`, `use_base64` — correct. `aws_vpc_security_group_ingress_rule` / `egress_rule` use `cidr_ipv4`, `from_port`, `to_port`, `ip_protocol`, `referenced_security_group_id` — correct, and `ip_protocol = "-1"` for all-traffic egress is valid. `data.aws_region.current.name` is correct under provider 5.x (the `.region` rename is a 6.x change). The top-level `check "quicksight_user_arn_requerido"` with an `assert` referencing `var.enable_quicksight` and `var.quicksight_user_arn` is valid Terraform (≥ 1.5); `check` blocks can reference variables and the condition expression here is well-formed.

QuickSight: `parameters { postgresql { host, port, database } }`, `credentials { credential_pair { username, password } }`, `vpc_connection_properties { vpc_connection_arn }`, `ssl_properties { disable_ssl }`, `physical_table_map { physical_table_map_id, relational_table { data_source_arn, schema, name, input_columns {} } }`, and the `permission` (singular, on `aws_quicksight_data_source`) vs `permissions` (plural, on `aws_quicksight_data_set` and `aws_quicksight_dashboard`) distinction all match the provider schema. The dashboard `definition { data_set_identifiers_declarations {}, sheets { visuals { bar_chart_visual { chart_configuration { field_wells { bar_chart_aggregated_field_wells {...} } } } } } }` nesting is correct for 5.60.
